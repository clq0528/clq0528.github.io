🔍 架构逻辑纠正：
1. Client (外部端)
身份：UI 渲染器。
逻辑：它不具备“思考”能力，只是通过 WS 协议将你的语音/文字发给网关，并把网关传回的流式文字显示出来。
2. Gateway (身体)
身份：宿主服务器。
逻辑：常驻后台。它负责“接线”，确保无论你从手机还是电脑连进来，都能找到对应的会话灵魂（Runtime）。
3. Runtime (大脑)
身份：逻辑执行单元。
逻辑：由 Gateway 动态创建。它负责分析 LLM 的回复，决定什么时候去跑代码（Sandbox），什么时候去读文件。
💡 为什么要把它们分开？
如果把 Agent Runtime 放在 Client（比如手机里），当你关掉手机应用时，正在执行的 npm install 或 Python 爬虫 就会中断。通过 Gateway 托管 Runtime，你可以用手机下个指令，然后去睡觉，任务在服务器后台继续运行，明天早上用 Mac 连上去看结果。
典型运行场景：你在外用手机（Client）让机器人处理服务器上的日志。

为什么同时保留“直连”与 SSH？
直连 WS (Direct WS)
  • 通过 Bonjour/Tailnet 自动发现
  • 配对令牌 + ACL 细粒度管理
  • 无需 Shell 访问，更安全可审计
SSH 回退 (SSH Fallback)
  • 跨网络通用的终极回退方案
  • 解决多播/mDNS 在复杂网络失效问题
  • 无需开启额外入站端口

HTTPS/REST 标准做法： 与云端服务交互时不使用 WS，而是标准的 API 调用。
核心场景：本地执行 (Pipe/Socket 为主)-运行本地脚本、操作 Docker 沙盒。

Stdio / Unix Socket 底层调用： 执行 exec 时，网关是通过操作系统管道（Pipe）或 Docker API 与子进程通信的。
总结：
  • WebSocket 仅用于 Client <-> Gateway 之间的“控制链路”。
  • HTTPS/REST 用于 Gateway <-> 云端 AI / Webhooks 之间的“数据链路”。
  • Pipe / Docker API 用于 Gateway <-> 沙盒/操作系统 之间的“执行链路”。

关键参数说明
待运行的 Shell 命令（必填） 自动转后台的延迟（默认 10000ms）。在此时间内的输出同步返回，超时则切后台。 若为 true，跳过前台等待，直接异步运行并返回 SessionID。 提权模式。若开启，指令将在 Docker 沙盒外的宿主机（Host）运行。 进程生命周期硬上限（默认 1800s）。

⚠️ 注意事项：
  • 隔离性：Process 工具具有智能体隔离性，Agent A 无法操作 Agent B 的进程。
  • 易失性：所有后台会话均在内存中，OpenClaw 进程重启后会全部丢失。
  • 同步：只有运行 poll 或 log 且结果被记入聊天记录，输出才会被保存到历史数据库。
