CAN 收发器"带硬件过滤"和"不带"，到底差在哪？

CAN 里的"过滤"有三个意思，别再只当成一个了。收发器管"电平"、控制器管"收数据"、PN 收发器管"醒 MCU"。

核心结论
经典 CAN 收发器不认报文 ID，它不做过滤；真正按 ID 过滤的是 CAN 控制器；而新一代收发器上的"唤醒过滤"，目的不是收数据，是省电。

两个反直觉的真实场景

场景一：电瓶亏电

一辆车停了一周没动，电瓶却没电了。查到最后，某个一直挂着电瓶的 ECU 半夜里自己醒了几次——没人碰它。

场景二：CPU 负载不均

两条 CAN 报文在总线上飞，节点 A 的 CPU 很闲，节点 B 的 CPU 却一直在跑。硬件差不多，差在哪？

这两个问题，都绕不开 CAN 里一个常被讲错的概念：硬件过滤。把过滤讲错的人，多半是把收发器和控制器混了。

三种"过滤"速览

角色管什么过滤目的典型器件
收发器电平转换经典款不过滤；PN 款决定是否唤醒 MCUTJA1050 / TJA1145
控制器数据链路层按 ID 决定收不收，降 CPU 负载SJA1000 / MCP2515 / bxCAN / M_CAN

关键：工程上说的"带硬件过滤"，绝大多数指 CAN 控制器带了硬件验收滤波。而"收发器带过滤"特指支持局部组网/选择性唤醒（PN）的收发器。

过滤到底发生在哪一层？

按 ISO 11898 分层，点击每一层查看详细职责。过滤不在收发器，在控制器。

MCU（应用层）
应用
运行应用代码，处理收到的报文数据，发送指令。

MCU 通过中断或轮询从 CAN 控制器的 RXFIFO 读取报文。带硬件过滤时，只有匹配的帧才进 FIFO、才触发中断，CPU 负载低。不带过滤时，所有帧都进 FIFO，CPU 必须在 ISR 里逐个读出来再软件判断 ID。

↕ TXD/RXD（SPI/并行）
CAN 控制器（LLC + MAC 数据链路层）
过滤在这里
组帧/解帧、CRC、位填充、验收滤波（Acceptance Filter）。

控制器内部有验收码（ACR/Filter）和验收屏蔽（AMR/Mask）寄存器。每收到一帧，硬件自动比较：(ID & Mask) == (ACR & Mask)。相等则存入 RXFIFO 并触发中断；不等则硬件直接丢弃，不进 FIFO、不中断 CPU。

不同控制器的过滤资源差异很大：SJA1000 有 ACR0-3+AMR0-3；MCP2515 有 2 屏蔽+6 过滤器；STM32 bxCAN 有 28 个过滤器组；TC3xx MCMCAN（Bosch M_CAN）有独立的过滤元素配置，且掩码极性与 SJA1000 相反。

↕ TXD/RXD（逻辑电平）
CAN 收发器（PMA 物理层）
电平转换
把 TXD/RXD 逻辑电平变成 CANH/CANL 差分信号，再变回来。经典款是"哑"器件。

经典收发器（TJA1050/TJA1042/TJA1043）：只做电平转换，不解析报文 ID，没有过滤能力。休眠时靠 WAKE 引脚或"唤醒模式脉冲"唤醒，基本是"总线有活动就醒"。

PN 收发器（TJA1145/TJA1445）：内部有硬件比较逻辑+唤醒过滤器，Sleep 模式下仍监听总线，只有匹配预设 ID 的唤醒帧才拉高 INH 引脚给 MCU 上电。目的是省电，不是收数据。

↕ CANH / CANL（差分信号）
CAN 总线（CANH / CANL）
传输介质
双绞线，差分信号传输，所有节点共享。报文广播到总线上所有节点。

总线是广播介质——一帧报文发出来，所有节点的收发器都能收到。验收滤波只决定"本节点收不收"，不影响报文照常广播到总线上。它只防"不相关帧进 FIFO"，不防链路层错误（那靠 CAN 自带的 5 种错误检测+错误帧）。

分层职责
收发器管"电平"、控制器管"收数据"、PN 收发器管"醒 MCU"——三者是不同层面的事，别张冠李戴。

带硬件过滤的好处

  • CPU 只在相关帧到达时才被打断，负载低
  • 总线负载高时也不会被无关帧撑爆 FIFO 而丢帧
  • 实时性好，中断次数可控

不带过滤的代价

  • 总线上所有帧都进 RXFIFO，CPU 必须在中断里逐个读出来再软件判断
  • CPU 占用高、中断频繁
  • FIFO/RAM 容易被无关帧占满，进而溢出丢帧（总线负载高时尤其致命）
  • 实时性下降

时序解读

没有硬件过滤时，控制器对每一帧都做同样的事：帧在总线上传输（约 0.2ms）→ 塞进 RXFIFO → 立刻拉 RX 中断 → MCU 进 ISR 读帧、读 ID → 软件比对 → 匹配则处理，不匹配则丢弃。

关键：哪怕这帧最后要被丢掉，MCU 也已经进了 ISR、读了 FIFO、比了 ID。三帧里只有一帧是自己的，但 MCU 进了三次中断、比了三次 ID。总线一忙，这些 ISR 会排队，FIFO 被无关帧占满就溢出丢帧。

如果带硬件过滤，只有 0x101 会触发中断，MCU 只进一次 ISR。0x205 和 0x1A0 在控制器硬件层就被丢弃了，根本不进 FIFO、不中断 CPU。

PN 收发器与选择性唤醒（TJA1145）

"收发器带过滤"是较新的说法，特指支持 ISO 11898-6 局部组网的收发器。目的不是收数据，是省电。

普通收发器 vs PN 收发器

特性普通收发器 (TJA1050/1042/1043)PN 收发器 (TJA1145/1445)

休眠唤醒方式WAKE 引脚 / 唤醒模式脉冲按 ID（+可选 DLC/数据）选择性唤醒
唤醒精度"总线有活动就醒"只匹配预设 ID 才醒

PN 唤醒工作流程

  1. MCU 通过 SPI 配置 TJA1145 的唤醒过滤器：ID 寄存器 + ID 掩码寄存器（+可选 DLC/数据掩码）
  2. MCU 进入 Sleep，TJA1145 也进入 Sleep 模式，但仍监听总线
  3. 总线上有帧到来时，TJA1145 硬件比较 ID 是否匹配预设
  4. 匹配 → 拉高 INH 引脚 → 给 MCU/外置 LDO 上电 → 唤醒节点
  5. 不匹配 → 继续 Sleep，不唤醒 MCU
掩码极性：TJA1145 的唤醒过滤器掩码位 = 1 同样是"不关心"，和 SJA1000 一致。
注意：过滤器配置在易失性寄存器里，收发器掉电后需 MCU 重新通过 SPI 配置。每次上电或唤醒后，都要重新配置 PN 寄存器再进低功耗。

实测效果

普通收发器休眠

静态电流约 12.8 mA，任何总线活动都唤醒，非必要唤醒频繁。

PN 收发器选择性唤醒

静态电流约 0.7 mA，非必要唤醒减少约 95%。

兼容 ISO 11898-6 局部组网标准。TJA1145/FD 变体还有 FD-passive：Sleep 模式直接忽略 CAN FD 帧，避免被 FD 通信误唤醒——这点对假唤醒很关键。

假唤醒排查清单

节点本不该醒，却因为无关帧、噪声或配置问题退出了休眠，白白耗电。常电节点电瓶亏电的头号原因之一。

7 大常见原因与解法（点击展开）

CAN FD 帧误唤醒 FD
原因：

普通 PN 收发器在 Sleep 监听时，收到 FD 帧（FDF 隐性、BRS 等），可能被误判为有效唤醒帧。

解法：

用带 FD-passive 的 TJA1145/FD，Sleep 模式直接忽略 FD 帧。

唤醒模式（wake-up pattern）误触发 配置
原因：

只开了 CAN 唤醒使能（CWE=1），却没使能选择性唤醒（CPNC=0）或 PN 配置无效（PNCOK=0），任何标准唤醒模式脉冲都会唤醒。

解法：

正确使能选择性唤醒（CPNC=1）并把 PN 寄存器配好（拿到 PNCOK=1）。

总线噪声 / 毛刺 / EMC 干扰 硬件
原因：

地弹、短促毛刺被误判为唤醒模式或帧。

解法：

做好屏蔽与接地、去抖、正确总线偏置，满足 ISO 7637-3 / ISO 11452 的抗扰要求。

ID 掩码配太宽 掩码
原因：

掩码 1 太多，很多不相关 ID 都能匹配，导致频繁唤醒；掩码全 1 甚至退化成"边沿触发"，任何相关格式帧都醒。

解法：

按需收紧掩码，只匹配网络管理（NM）报文所在 ID 段。

配置丢失 / 没配 配置
原因：

TJA1145 的过滤器在易失寄存器里，断电后清空；若 MCU 没重新 SPI 配置就进 Sleep，默认状态可能"全收"。

解法：

每次上电或唤醒后，都重新配置 PN 寄存器再进低功耗。

只配 ID 没配 DLC/数据 精度
原因：

同 ID 但内容不符的帧也唤醒。

解法：

把 DLC + 数据掩码也配上，进一步收窄唤醒条件。

网络管理报文风暴 NM
原因：

NM 设计不当，唤醒后不及时休眠、节点互相唤醒。

解法：

规范 NM 超时与休眠策略，避免唤醒风暴。

规避假唤醒一句话

最佳实践
PN 收发器 + FD-passive 型号 + 窄掩码（只认 NM 报文 ID）+ 每次上电重配 SPI + 良好 EMC 设计，基本能灭掉假唤醒。

普通 PHY 板子的三条现实路子

如果你的收发器是 TJA1043 这种普通 PHY，深休眠下无法按 ID 选择性唤醒——这是硬件限制，不是配置技巧。

为什么深休眠下 MCMCAN 挡不住？

节点进深休眠，MCMCAN 的时钟会被停掉（CCCR.CSR 时钟停止，硬件回 CCCR.CSA=1 确认）。这时候 MCMCAN 的验收过滤器根本没在跑——控制器都没上电，谈不上挡帧。

真正守在总线边上的是收发器。普通收发器只看"有没有活动"，看不懂 ID。总线上来一帧 0x100，它照样把 RXD 拉活、把 MCU 叫醒，跟别的帧没区别。

结论：深休眠 + 普通收发器，0x100 来了照样醒你，MCMCAN 那时是"聋"的，挡不住。

落到你的需求

"唤醒后需要收 0x100"这一半一直没问题——醒来把 0x100 放进 MCMCAN 验收表放行即可。

"休眠不希望 0x100 唤醒"才是矛盾点：

  • 要深休眠省电 → 走 A（容忍假唤醒，醒来软件再睡）
  • 要严格不被吵醒 → 走 B（轻休眠费电，MCMCAN 保活过滤）
  • 想深休眠又按 ID 选择性 → 走 C（换 PN 收发器）
提醒：前面讲的 TJA1145 选择性唤醒是"有 PN 收发器时"的解法；如果你的板子只有普通 PHY，深休眠的 ID 选择性唤醒靠 MCMCAN 单枪匹马解决不了，得在上面三套方案里选。

经典收发器

是"哑"的，只管电平转换，不认 ID。TJA1050/1042/1043 没有过滤能力。

控制器验收滤波

管"收不收数据"，用来降 CPU、防丢帧。ACR+AMR 硬件比较，不匹配直接丢弃。

PN 收发器

管"醒不醒 MCU"，用来省电。TJA1145 按 ID 选择性唤醒，静态电流 0.7mA。

掩码极性

SJA1000/STM32：掩码=1 不关心；M_CAN(TC3xx)：相反，掩码=1 必须匹配。移植别整反。

假唤醒

常电节点电瓶亏电头号原因。靠 FD-passive + 窄掩码 + 重配 SPI + 良好 EMC 化解。

普通 PHY 深休眠

无法按 ID 选择性唤醒。三选一：假唤醒再睡 / 轻休眠保活 / 换 PN 收发器。

量产 ECU

用控制器硬件验收滤波，按功能分配 ID 段，配好掩码，别让 CPU 去"软过滤"。

调试/嗅探

临时把过滤设成"全收"监听整网。量产节点一般不这么做。

两层边界

验收滤波只决定"收不收"，不影响报文广播；不防链路层错误（那靠错误检测+错误帧）。

一句话记住
收发器管"电平"、控制器管"收数据"、PN 收发器管"醒 MCU"——CAN 里的"过滤"有三个意思，别再只当成一个了；而"深休眠按 ID 唤醒"只有第三个（且得是 PN 收发器）才办得到。
